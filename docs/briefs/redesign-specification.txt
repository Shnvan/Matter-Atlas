============================================================
1. PRIMARY PROBLEM WITH THE CURRENT UI
============================================================

The existing interface is clean but visually resembles:

- developer documentation
- an internal project dashboard
- a dark SaaS/admin interface

It does NOT yet feel like an interactive scientific object-learning product.

The current hero gives too much space to:

- a giant title
- project-memory links
- documentation cards
- prose

and too little space to the Arduino Uno itself.

The learner should see and interact with the Arduino almost immediately.

The public learner experience must not look like the repository's internal
documentation interface.

Move developer/project-memory documentation into a separate internal route,
section, or clearly secondary area.

Do NOT delete the documentation.

============================================================
2. NEW ART DIRECTION
============================================================

Design the product as:

SCIENTIFIC ATLAS
×
INDUSTRIAL DESIGN STUDIO
×
INTERACTIVE MUSEUM EXHIBIT
×
MODERN PRODUCT INTERFACE

The experience should feel calm, tactile, premium, highly considered, and
scientifically credible.

Core principle:

QUIET INTERFACE.
RICH OBJECT.

The object being studied must contain most of the visual complexity.

The surrounding UI should almost disappear until needed.

Avoid the common AI-generated aesthetic.

DO NOT default to:

- huge gradients
- neon glow
- glassmorphism everywhere
- oversized pill buttons
- dozens of identical cards
- "bento grid" for everything
- giant SaaS hero text
- blue-black developer dashboard styling
- cyan outlines around every container
- decorative floating particles
- meaningless blur blobs
- excessive shadows
- every section inside a rounded rectangle
- animation without semantic meaning

No "card soup."

11. ISOLATE VS HIDE
============================================================

Implement these as different concepts.

Selected component remains fully visible.

============================================================
14. MOTION DESIGN
============================================================

Use animation only to communicate:

- hierarchy
- causality
- scale
- spatial relationship
- state change
- assembly
- disassembly
- signal propagation

Good:

component rises from board
camera approaches component
PCB layers separate
package opens
die becomes visible
signal follows copper trace
MOSFET channel appears
electric field changes
electron/hole states change

Bad:

random floating particles
constant glowing
decorative bouncing
everything sliding in on page load
animations whose only purpose is visual spectacle

Prefer natural ease or critically damped spring behavior.

Most UI microinteractions should complete around 120-250 ms.

Larger object/camera transitions may be slower when necessary to preserve
orientation.

Always respect prefers-reduced-motion.

31. ACCEPTANCE TEST
============================================================

The final product should NOT feel like:

an internal documentation portal.

It should feel like:

"I placed an Arduino Uno under an extraordinary interactive scientific
microscope."

Within five seconds a new visitor should understand:

1. This is an Arduino Uno.
2. I can touch/click its parts.
3. I can learn what every part does.
4. I can go inside those parts.
5. I can eventually reach transistors, silicon, atoms, electrons, and photons.

The user should be able to follow:

Arduino
→ ATmega328P
→ package
→ die
→ CPU/circuit
→ logic
→ transistor
→ doped silicon
→ lattice
→ atom
→ electron

while always understanding:

WHAT AM I LOOKING AT?

WHAT IS IT MADE OF?

HOW DOES IT WORK?

The user should also be able to follow parallel physical branches such as:

Arduino
→ LED
→ p-n junction
→ carriers
→ photon

without being taught false hierarchy.
